从工作区 AGENTS.md 或各仓研发入口定位事实源：平台程序维护框架及功能代码；数据仓维护运行产生的配置与证据；管理 HOME 维护管理身份与方法；业务仓维护原生 Harness 文件及其 MCP 配置。

1. 列明本次用户目标、涉及仓库和直接消费者。用现有调用链核对归属，不以文件名猜测。不要把业务身份加载成当前研发身份。
2. 先改唯一实现或配置来源，再修改消费者。保持 DSH 原生文件合同；不复制运行配置进程序仓，不把 Harness 存数据库。跨仓引用使用明确来源，Skill 不读取其他包私有文件。
3. 在真实工作树验证最小完整任务：实现检查、消费者装载、实际运行与结果。需要管理助手参与的能力回到管理助手复验。模拟及外部不可达结果分别说明。
4. 核对每仓 diff、文件来源、提交依赖和必要锁定。源码提交先于引用它的锁文件；工作区固定来源最后更新。按用户授权提交推送，报告各仓提交及尚未验证的业务效果。

## 五仓提交说明合同

控制仓和四个子仓都使用同一提交说明标准，不因改动大小省略事实：

- 标题使用“动作 + 对象/结果”，让提交列表能够独立说明做了什么。
- 新增特性在正文说明新增能力、使用边界和直接消费者；问题修复说明问题表现、根因、影响范围和关键验证结果。
- 跨仓变更说明各仓职责、提交依赖顺序、锁定版本及尚未验证的外部或业务效果。
- 提交前只暂存本次授权范围，检查 `git diff --cached --check` 和暂存 diff；推送后核对对应远端 `main` SHA，并在交付回执中逐仓列出。

不要使用只有“更新代码”“修复问题”“同步版本”而没有正文事实的泛化备注。若确实只是机械版本锁定，也要在正文写明被锁定的来源、原因和验证方式。
